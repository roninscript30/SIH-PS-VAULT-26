# Formal Provenance Model & Data Governance Contract

> **SIH PS Vault 2026** · Data Provenance Levels, Trust Hierarchy & Conflict Protocols

---

## 1. Provenance Classifications

To ensure information integrity and prevent AI hallucination, all data within the repository is explicitly assigned to one of five formal **Provenance Levels**:

```
 ┌─────────────────────────────────────────────────────────────┐
 │ 1. SOURCE          (Official ground-truth text & metadata)  │
 ├─────────────────────────────────────────────────────────────┤
 │ 2. DERIVED         (Deterministic rule-based enrichment)    │
 ├─────────────────────────────────────────────────────────────┤
 │ 3. GENERATED       (Rendered markdown notes & catalogs)     │
 ├─────────────────────────────────────────────────────────────┤
 │ 4. ANALYSIS        (Evaluations & heuristic scoring)        │
 ├─────────────────────────────────────────────────────────────┤
 │ 5. RECOMMENDATION  (Proposed solutions & team matches)      │
 └─────────────────────────────────────────────────────────────┘
```

### Detailed Level Specifications

| Level | Definition | Examples | Trust Level | How Created | Regenerable? | Agent Editable? |
| :--- | :--- | :--- | :---: | :--- | :---: | :---: |
| **SOURCE** | Direct official information from SIH organizers | PS ID, Title, Nodal Org, Dept, Theme, Category, Official Description | **100% (High)** | Scraped modal HTML / Portal APIs | ❌ No | ❌ **PROHIBITED** |
| **DERIVED** | Deterministic inferences generated by repository tooling | Technology tags, Sector domains, Org Type, Has Dataset flag | **80-90% (Medium-High)** | Keyphrase regex matching (`vault_config.py`) | ✅ Yes | ⚠️ Via Generator / Config Only |
| **GENERATED** | Renders and index views constructed from dataset | `PS-26001.md`, `theme_index.md`, `all_problems_index.md` | **100% (of Source)** | Vault generation orchestrator (`generate_vault.py`) | ✅ Yes | ❌ **PROHIBITED** (Patch Generator Instead) |
| **ANALYSIS** | Evaluative heuristics, complexity scoring, domain insights | Technical difficulty score, dataset quality assessment | **60-70% (Medium)** | Algorithmic or heuristic evaluations | ✅ Yes | ⚠️ With Explicit Disclaimer |
| **RECOMMENDATION** | Agent or human recommendations | Team fit, architecture proposal, tech stack recommendation | **Inferred** | Reasoning engines, LLM prompts | N/A | ✅ Allowed (Marked as Inference) |

## 2. Tiered Data Authority Hierarchy

Information flows strictly down a 6-tier authority hierarchy:

```
Tier 1: Official Live SIH Portal (https://www.sih.gov.in/sih2026PS)
         │ [Primary authority when live]
         ▼
Tier 2: Raw Source Snapshot (data/sih2026_raw.html)
         │ [Local offline HTML snapshot of live portal modal dialogues]
         ▼
Tier 3: Normalized Ground-Truth Dataset (data/sih2026_problem_statements.json)
         │ [Cleaned, UTF-8 encoded, structured JSON dataset]
         ▼
Tier 4: Vault Problem Statement Notes (01-Problem-Statements/*.md)
         │ [Generated Markdown notes with YAML frontmatter & cross-links]
         ▼
Tier 5: Generated Indexes & Taxonomy Catalogs (02-Themes/, 06-Indexes/, etc.)
         │ [Master tables, theme catalogs, technology hubs]
         ▼
Tier 6: Downstream Analysis & Inferences (Agent reasoning, solutions, rankings)
```

### Snapshot vs. Live Portal Authority Rules

- **Local Snapshot (`data/sih2026_raw.html`)**: Serves as verifiable evidence of the portal state at the time of extraction. It provides offline reproducibility.
- **Live Portal (`https://www.sih.gov.in/sih2026PS`)**: Remains the ultimate official authority. If the live portal updates problem statements, the local raw snapshot must be updated via the extraction scraper, followed by standard normalization and regeneration.
- **Local snapshot is NOT permanently authoritative** over a verified live portal update.

## 3. Conflict Resolution Protocol

When data discrepancies or conflicts occur, agents and maintainers must strictly follow this protocol:

### Scenario 1: Source HTML and Normalized JSON Disagree
- **Cause**: Text cleaning, encoding repair, or regex parsing anomaly.
- **Resolution**:
  1. Inspect `data/sih2026_raw.html` modal text for the affected PS ID.
  2. Verify if the difference is due to CP1252 encoding repair or actual content modification.
  3. Update `scripts/verify_data.py` / normalization functions if necessary.
  4. **Do NOT manually patch JSON without verifying against raw source HTML.**

### Scenario 2: Markdown Note and JSON Dataset Disagree
- **Cause**: Manual edit to a generated Markdown file or incomplete build execution.
- **Resolution**:
  1. `data/sih2026_problem_statements.json` is CANONICAL.
  2. Re-run `python scripts/generate_vault.py` to regenerate the Markdown file from the canonical JSON dataset.
  3. **Never edit the Markdown file directly to resolve a JSON disagreement.**

### Scenario 3: Derived Classification Appears Incorrect (e.g. False Positive Tech Tag)
- **Cause**: Overly broad keyphrase regex in `scripts/vault_config.py`.
- **Resolution**:
  1. Do NOT manually edit individual Markdown notes.
  2. Refine the regex pattern in `TECH_KEYWORDS` or `DOMAIN_KEYWORDS` inside `scripts/vault_config.py`.
  3. Re-run `generate_vault.py` and `verify_data.py`.

### Scenario 4: Generated Artifacts Disagree with Source Data
- **Cause**: Generator script bug or outdated index file.
- **Resolution**:
  1. Fix the template or generator logic in `scripts/vault_generators.py` or `scripts/generate_vault.py`.
  2. Regenerate the entire vault.

## 4. Golden Rule of Uncertainty

> [!CAUTION]
> **NEVER SILENTLY OVERWRITE UNCERTAINTY**
> 
> If an agent encounters conflicting data between sources, ambiguous metadata, or uncertain classifications:
> 1. Preserve both data points or log the discrepancy.
> 2. Clearly state the source of each conflicting claim.
> 3. Mark the conclusion explicitly as an **INFERENCE** or **UNRESOLVED CONFLICT**.
> 4. Report the discrepancy to the maintainers rather than making unauthorized edits to official metadata.
